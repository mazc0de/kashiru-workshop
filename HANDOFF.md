## Cara bekerja dengan user

- Gunakan bahasa Indonesia.
- **Nama file, folder, dan semua nama di kode dalam bahasa Inggris** (R26), memakai padanan Inggris di GLOSSARY. URL route juga bahasa Inggris (R27). Label dan teks yang tampil ke pengguna, komentar, judul tes, nilai di database, serta kolom dan parameter RPC tetap bahasa Indonesia.
- **Jangan menjalankan Supabase lokal/Docker.** Tulis SQL di `supabase/migrations/`, verifikasi sendiri dengan PGlite, lalu berikan daftar file yang user tempel di SQL Editor Supabase online.
- **Satu pertanyaan per pesan**, dengan rekomendasi yang bisa diterima cukup dengan "ya". User biasanya menjawab "ya sesuai saran anda" atau memberi koreksi singkat.
- Detail yang belum diputuskan selalu **ditanyakan**, sekecil apa pun, bukan diisi sendiri. Yang boleh langsung diterapkan hanya koreksi tanpa alternatif.
- Sebelum menyatakan "tidak ada pertanyaan lagi", **baca ulang seluruh PRD revisi** untuk mencari celah. Pada sesi desain, kesimpulan "selesai" sempat dua kali terlalu cepat.
- Arah cakupan user konsisten: _"aplikasi ini hanya untuk mencatat penjualan kasir"_, untuk satu bengkel kecil dengan satu laptop. Kalau ragu, tawarkan opsi yang paling sederhana.
- Setiap keputusan baru langsung dicatat di PRD revisi. Perbarui juga GLOSSARY kalau ada istilah baru, dan ADR kalau keputusannya sulit dibalik, mengejutkan, dan hasil trade-off nyata.

## Keputusan yang mudah "diperbaiki" secara keliru

Hal-hal di bawah ini disengaja, walaupun terlihat seperti kekurangan:

- **Nomor nota** dibuat di laptop yang membuat nota, bukan oleh sequence database, karena nota tetap dibuat saat offline (PRD 7.5). Sejak R50 semua laptop boleh membuat nota tanpa kode perangkat di nomornya; nomor yang bentrok diganti server ke nomor kosong berikutnya, dan itu disengaja.
- **Stok boleh minus**, karena nota tidak boleh tertahan oleh stok sistem yang belum benar (PRD 4.3).
- **Mutasi stok mencatat HPP, bukan harga jual.** Contoh SQL di PRD awal keliru (PRD 8).
- **Selisih opname** dihitung terhadap stok sistem pada waktu tiap part dihitung, bukan snapshot saat sesi dibuka (PRD 4.5).
- **Tidak ada SKU.** Produk unik berdasarkan nama + merek. Barcode internal berupa angka urut Code128 (PRD 4.2, 4.9).
- **Satu metode bayar per nota**, hanya sebagai catatan, tanpa split dan tanpa referensi (PRD 4.6).
- **Nota dan penerimaan tidak pernah diedit.** Koreksinya lewat void seluruh dokumen. Nota offline yang gagal terkirim tidak bisa dihapus (PRD 4.7, 4.13).
- **Tanggal faktur penerimaan** hanya keterangan. Mutasi stok selalu dibukukan pada waktu penerimaan disimpan (PRD 4.4).
- **Tidak ada Realtime dan tidak ada pemeriksaan berkala.** Semua perubahan data master terjadi di laptop kasir (PRD 4.13).
- **Supabase Free.** PITR tidak tersedia, jadi backup lewat GitHub Actions (ADR 0005).
- **Nama database tetap bahasa Indonesia walaupun kode berbahasa Inggris (R26, R27).** Kolom, nilai (`'tunai'`, `'dibuka'`), parameter RPC (`p_*`), dan kunci JSON di dalamnya (`p_items: [{ product_id, qty, harga }]`) mengikuti SQL yang sudah dijalankan. Tipe yang mencerminkan baris database sengaja memakai nama kolom: `ServerProductRow` (`src/lib/localCopy.ts`), `SessionRow` (`src/stocktake/data.ts`), parameter `toSummary` (`src/pos/sales.ts`), `DbRow` (`src/settings/masterData.ts`), dan `Profile`/`ChangeLogEntry` di Edge Function. Format permintaan `manage-accounts` (`aksi`, `nama`, `user_id`, jawaban `pesan`) juga tetap, karena fungsinya sudah ter-deploy. Payload checkout disusun satu tempat di `buildCheckoutArgs` dan diuji paritas terhadap SQL.
- **Grafik omzet memakai dua oranye** (part pekat, jasa muda), bukan warna kedua, dan warna jasa sengaja di bawah 3:1 terhadap kartu terang. Kompensasinya legenda, tooltip, dan tampilan tabel; jangan dihapus (pilihan teknis 21).
- **Trigger dimatikan per tabel, bukan lewat `session_replication_role`.** Role `postgres` di SQL Editor dan Session pooler Supabase tidak boleh mengubah parameter itu (galat 42501), tetapi boleh `ALTER TABLE … DISABLE TRIGGER` karena pemilik tabel. File backup (format 2), `npm run restore`, `supabase/seed/dummy-data.sql`, dan `reset-data.sql` memakai cara ini, dan diuji dengan role pemilik tabel yang bukan superuser (`asTableOwner` di `supabase/tests/harness.mjs`). Foreign key tetap diperiksa, jadi urutan `BACKUP_TABLES` harus mengikuti foreign key. Setiap tabel baru di skema public wajib masuk `BACKUP_TABLES`; uji `backup.roundtrip.test.ts` gagal kalau ada yang terlewat.
- **Ekspor laporan = isi layar.** Bagian laporan didefinisikan sekali (`tableSection`/`summarySection`) dan dipakai untuk layar, Excel, dan PDF. Jangan membuat definisi ekspor terpisah.
- **Riwayat skema Dexie versi 1–3 memakai nama tabel Indonesia** dan tidak boleh diubah; versi 4 menyalin data ke tabel berbahasa Inggris dan versi 5 menghapus tabel lama (`src/lib/localMigration.ts`).

## Langkah berikutnya

Ikuti fase di [`IMPLEMENTATION-PLAN.md`](./IMPLEMENTATION-PLAN.md). Setelah user memastikan SQL Fase 1 berjalan tanpa error di Supabase online:

1. **Pastikan user sudah** menjalankan `20261019000008_backup_logs.sql` dan `20261019000009_any_device_sales.sql`, dan, kalau `manage-accounts` versi PIN sempat di-deploy, **deploy ulang versi sekarang** (versi dashboard di `supabase/dashboard/manage-accounts.ts`).
2. **Uji pemulihan ke project sungguhan** (kriteria Fase 9): buat project Free kedua, migrasi, lalu `npm run restore` dengan file dari Pengaturan → Backup. Yang belum bisa dibuktikan tanpa Supabase sungguhan: `set session_replication_role` lewat Session pooler dan `admin.createUser({ id })`; keduanya mengikuti dokumentasi Supabase.
3. **Deploy Vercel** setelah user membuat repo dan commit.
4. **UI** (untuk layar baru): ikuti `.claude/skills/design-taste-frontend/references/app-screens.md` dan sheet `achromatic-ledger` (`node .claude/skills/design-taste-frontend/scripts/draw.mjs --show --out .taste-skill/app`). Periksa setiap layar dengan `inspect.mjs --app`.
5. **Fase 0** dijalankan begitu printer dan scanner tersedia.

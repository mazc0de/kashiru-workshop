# Rencana Implementasi Kashiru

18 Oktober 2026 · Status: **disetujui user (19/10/2026)**, keputusan R2–R10 masih ditanyakan

Rencana ini disusun dari [`PRD-Kashiru-revised.md`](./PRD-Kashiru-revised.md). Kalau ada perbedaan, PRD revisi yang berlaku. Keputusan yang muncul selama penyusunan ada di bagian 4 dan ditanyakan satu per satu.

## 1. Prinsip

- **Database dulu.** Aturan stok, average cost, nomor dokumen, dan void ditulis sebagai fungsi Postgres sebelum ada layar. **Tanpa Supabase lokal** (keputusan user 19/10/2026): developer memverifikasi SQL di Postgres sementara (PGlite), lalu user menempel SQL di SQL Editor Supabase online.
- **SQL disimpan sebagai file migrasi** di `supabase/migrations/`. Untuk instalasi pertama, user menjalankan file-file itu berurutan di SQL Editor Supabase. Skrip `npm run setup` (PRD 7.7) nanti memakai file yang sama untuk bengkel berikutnya.
- **Satu fase selesai dan dicoba sebelum fase berikutnya.** Setiap fase punya kriteria selesai.
- Istilah di kode, nama tabel, dan copy UI mengikuti [`GLOSSARY.md`](./GLOSSARY.md).

## 3. Pilihan teknis

Pilihan berikut tidak mengubah perilaku yang tertulis di PRD. Semuanya ikut disetujui bersama rencana ini, dan bisa dikoreksi satu per satu.

**Database**

1. **Tipe angka**: nominal transaksi (harga jual, diskon, subtotal, total, uang diterima, kembalian, harga beli penerimaan) memakai `bigint` dalam rupiah penuh. Harga beli rata-rata dan HPP memakai `numeric(14,2)` supaya rata-rata tidak bergeser karena pembulatan, tetapi tetap tampil tanpa desimal. Qty memakai `numeric(12,2)`.
2. **Kunci**: `uuid` untuk tabel master dan dokumen. `bigint identity` untuk `stock_movements` dan `change_logs`, supaya urutan catatan jelas untuk kartu stok.
3. **Jalur penulisan**: data master (kategori, mekanik, supplier, produk, barcode, kode part, pengaturan) ditulis langsung lewat API Supabase dengan RLS. Semua yang menyentuh stok atau nomor dokumen hanya lewat RPC `security definer`. Part baru dibuat lewat RPC `create_product` supaya produk, barcode, kode part, dan mutasi stok awal tersimpan dalam satu transaksi.
4. **Riwayat perubahan** untuk data master dan pengaturan dicatat oleh trigger database, sehingga tidak bergantung pada frontend. Void, penyesuaian, dan opname dicatat oleh RPC-nya.
5. **Append-only**: `stock_movements` dan `change_logs` dikunci trigger dari UPDATE dan DELETE, termasuk untuk service role.
6. **Angka nota**: server menyimpan angka yang dikirim Perangkat Kasir (angka yang tercetak di struk), setelah memeriksa konsistensinya: jumlah baris = subtotal, total = subtotal − diskon nota, total alokasi = diskon nota, dan tidak ada angka negatif. Rumus hitung nota ditulis sekali di TypeScript dan diuji.
7. **Sisa pembulatan alokasi diskon nota** dibagikan satu rupiah per baris ke baris dengan pecahan terbesar. Diubah dari "ke baris dengan nilai terbesar" saat menulis SQL, karena cara itu bisa membuat alokasi melebihi nilai baris kalau diskon nota hampir 100%.
8. **Toleransi jam Perangkat Kasir**: validasi masa tugas memberi kelonggaran 10 menit di batas awal dan akhir, karena `dibuat_pada` memakai jam laptop sedangkan `mulai`/`selesai` memakai jam server.
9. **Pencarian**: nopol punya kolom kunci (huruf besar tanpa spasi) dengan indeks. Pencarian produk di server memakai indeks `pg_trgm`.
10. **Auth**: pendaftaran publik dan konfirmasi email dimatikan di pengaturan Supabase Auth. Akun hanya dibuat lewat Edge Function `manage-accounts`. Akun yang tidak terdaftar di `profiles`, atau nonaktif, tidak bisa membaca apa pun karena RLS.
11. **Logo** disimpan di bucket Storage privat `logo` yang hanya bisa dibaca akun aktif, lalu disalin ke Dexie supaya tetap tercetak saat offline.
12. **Cakupan opname** dihitung saat tinjau, jadi part yang dibuat selagi sesi terbuka ikut masuk. Diskon persen 0–100 dengan paling banyak 2 angka desimal.

**Frontend**

13. npm sebagai package manager. Stack sesuai PRD 7.1, TypeScript mode strict.
14. Vitest untuk logika murni: hitung nota dan diskon, nomor nota, format nopol, deteksi scan, format rupiah dan qty. Layar diuji manual dengan pre-flight taste-skill.
16. **Nama file, folder, dan semua nama di kode berbahasa Inggris** (keputusan user 19/10/2026, R26): fungsi, komponen, hook, tipe, variabel, konstanta, dan properti objek, mengikuti padanan Inggris di GLOSSARY (mis. `hitungNota` → `calculateSale`). URL route juga bahasa Inggris (R27), mengikuti nama file layar (`/pos`, `/sales`, `/products`). Nilai teks yang hanya hidup di kode ikut bahasa Inggris (mis. `tone="error"`). Tetap bahasa Indonesia: label dan semua teks yang tampil ke pengguna, komentar, judul tes, nilai yang disimpan di database, nama kolom dan parameter RPC, serta format permintaan ke Edge Function `manage-accounts`.
17. **Antrean nota** (Fase 7): tabel Dexie `saleOutbox`; stok di salinan = stok server − qty antrean (R25). Pengiriman antrean dan muat ulang salinan memakai satu kunci (Web Locks, juga antar-tab) supaya nota yang baru terkirim tidak terhitung dua kali. Selama masih ada nota menunggu, pengiriman dicoba lagi setiap 30 detik saat online. Nota dianggap **ditolak** hanya untuk galat isi dari server (P0001, 22xxx, 23xxx); jaringan, server mati, token kedaluwarsa, dan akun pengirim nonaktif (42501) dicoba lagi tanpa menandai nota gagal.
18. **Sesi saat offline**: Supabase Auth menahan semua permintaan sampai ±30 detik selama mencoba memperpanjang token yang kedaluwarsa, lalu melaporkan sesi kosong walaupun login belum berakhir. Karena itu sesi dan profil tersimpan langsung dipakai saat aplikasi dibuka, dan server memperbaruinya di belakang layar. Status Perangkat Kasir dan pencocokan nomor urut dibatasi 3 detik. Pengiriman nota langsung dianggap offline kalau browser melaporkan offline; batas 10 detik (R23) berlaku saat Wi-Fi tersambung tetapi internet mati.
19. **Migrasi data perangkat setelah R26**: Dexie versi 4 menyalin isi tabel lama (`produk`, `antreanNota`, …) ke tabel berbahasa Inggris dalam bentuk baru, versi 5 menghapus tabel lama; kunci localStorage lama dipindah saat aplikasi dibuka (`src/lib/localMigration.ts`). Nota yang belum terkirim tidak boleh hilang dalam migrasi apa pun.
20. **Laporan** (Fase 8): angka dihitung fungsi SQL migrasi 7 (`security invoker`, jadi RLS tetap berlaku). Fungsi yang bisa lebih dari 1.000 baris (per hari, per produk, nilai persediaan) diambil per 1.000 baris dengan urutan pasti, karena batas baris Data API juga berlaku untuk fungsi. Setiap laporan disusun dari satu daftar bagian yang dipakai untuk layar, Excel (satu sheet per bagian), dan PDF (bagian berurutan), jadi isi ekspor selalu sama dengan yang tampil (`src/reports/sections.tsx`).
21. **Warna grafik omzet**: dua langkah dari hue aksen, bukan warna kedua, supaya Color Consistency Lock (PRD 6) tetap terjaga. Terang: part #c2410c, jasa #f2884b; gelap: part #e07227, jasa #a04f27 (token `--chart-part`/`--chart-service`). Diperiksa dengan validator palet skill dataviz: semua lolos kecuali kontras jasa terhadap kartu terang (2,5:1), sehingga grafik selalu berlegenda, bertooltip, dan punya tampilan tabel.
22. **Backup manual** (Fase 9, R45): file `.sql` dibuat di browser dari 21 tabel lewat Data API (per 1.000 baris, urut kunci utama). Satu pernyataan per baris (teks memakai `E''`), trigger buatan Kashiru dimatikan per tabel saat pemulihan (`ALTER TABLE … DISABLE TRIGGER USER`, cukup hak pemilik tabel; Supabase menolak `session_replication_role` untuk role postgres) dan foreign key tetap diperiksa, kolom identity memakai `overriding system value` lalu sequence diset ulang, tabel satu baris yang diisi migrasi di-upsert. Karena tabel dibaca satu per satu, isinya diperiksa utuh (baris nota tanpa nota, nota tanpa baris, saldo stok ≠ jumlah kartu stok, kartu stok tanpa dokumen) dan pembacaan diulang sampai 3 kali. `npm run restore` (Node + `pg`, lewat Session pooler) memeriksa project tujuan sudah dimigrasi dan kosong, membuat ulang akun lewat Admin API dengan ID yang sama, lalu menjalankan isi file dalam satu transaksi. Diuji pulih-ulang dengan skema asli di PGlite dan ujung ke ujung lewat protokol Postgres (PGlite socket server) dengan API admin tiruan.
15. Git sudah di-init tanpa commit. **User sendiri yang membuat commit dan repo GitHub di akhir** (keputusan user 19/10/2026), jadi deploy Vercel menunggu itu.
